## P1 corregido — Clasificación posterior cambiaba una utilidad histórica sin incluir el gasto

Ubicación revisada: `apps/api/src/services/owner-intelligence.service.ts`, llamada a `expenseCashOutflows` y bucle de gastos; `apps/api/src/services/operating-expense.service.ts`, `expenseCashOutflows`.

Caso reproducido:

1. Sucursal `America/Mexico_City`; salida `GASTO_MENOR`, efectivo −25, fecha **1/oct/2026 16:00 UTC**, sin clasificación.
2. Consultar período **1–2/oct/2026**: corte **3/oct/2026 06:00 UTC**. Sin ventas ni gastos clasificados, la respuesta correcta protege la estimación: utilidad `null`, advertencia de salidas sin clasificación.
3. Agregar una clasificación del mismo registroCajaId, gasto RENTA 25 con fecha declarada del movimiento, pero `creadoEn` **4/oct/2026 16:00 UTC**, posterior al corte.
4. Repetir exactamente la consulta histórica: el gasto se excluye correctamente por `creadoEn >= corte`, pero la detección de salidas sin clasificación usa vínculos actuales de todos los gastos/correcciones. El movimiento desaparece de la advertencia aunque su clasificación no existía al corte.

Resultado observado, antes → después:

```json
{
  "gastosOperativos": [0, 0],
  "utilidadOperativaEstimada": [null, 0],
  "datosInsuficientes": [
    ["Salidas de caja sin clasificación de gasto o compra."],
    []
  ],
  "corte": "2026-10-03T06:00:00.000Z"
}
```

Esto incumple la base anunciada de reconstruir evidencia conocida al corte: muestra un importe de utilidad como acreditado aunque la salida sigue sin clasificación histórica. Es un defecto de reporte; la prueba no alteró dinero real ni identificó una duplicación de caja.

## Corrección autorizada y comprobada

Único archivo de producto editado: `apps/api/src/services/owner-intelligence.service.ts`.

Para este reporte histórico, las salidas negativas de efectivo se consultan en su sucursal entre inicio y corte. Un vínculo se considera acreditado únicamente si el gasto existía antes del corte; las correcciones vinculadas también deben existir antes del corte y pertenecer a esos gastos conocidos. El listado operativo de salidas disponibles de PC-13 conserva sus reglas actuales. El cálculo de importes y las correcciones históricas existentes no cambian.

Prueba reproducible: `scripts/qa_owner_intelligence_history.cjs` usa `createTestFixture` y el servicio real compilado; acepta PostgreSQL únicamente con URL protegida y cliente separado. Cinco casos ejecutados:

1. Salida sin clasificación conserva utilidad `null` y la advertencia.
2. Clasificación posterior al corte conserva exactamente las mismas finanzas históricas; no agrega caja.
3. Clasificación anterior al corte incluye 25 una vez y conserva ocupación de capacidad cero como porcentaje `null`.
4. Corrección posterior de 25 → 30 con compensación −5 afecta el período posterior, mientras el anterior conserva 25; no se borra el original ni se duplica efectivo.
5. Salidas de otra sucursal no afectan el cálculo; un artículo nuevo conserva `SIN_HISTORIAL` y cobertura `null`; barbero no accede a inteligencia.

Fuente congelada y entregada al coordinador. No se modificó `operating-expense.service.ts`, esquema, rutas ni API web.
